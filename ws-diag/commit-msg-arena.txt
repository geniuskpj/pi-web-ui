feat(peers): arena.ai as a peer BACKEND on the same code path (no second implementation)

User instruction: "rather than make new codes, use the same api/codes for subagent (both pi/arena)".
So there is no arena peer path: a peer is still ONE session with a role and a pi-agent-core Agent — the
only difference is the `streamFn` and the model object the Agent is built with.

* lib/arena-stream.mjs (new, the whole arena surface):
  - `parseModelSpec()` — `arena/<slug>` / `arena:<slug>` selects the backend, anything else is a pi id
    (a half-spec like "arena/" is null, never silently treated as a pi model);
  - `arenaModel(slug)` — a model object so the session header, UsageBar and picker read normally;
  - `makeArenaStreamFn()` — a real pi-ai streamFn (start → text_start → text_delta → text_end → done, or
    an `error` event), built against the reference implementation in pi-ai's faux provider;
  - `createArenaBridge()` — the CDP runner: ONE tab ⇒ ONE call at a time (a single promise chain),
    lazy import of `ws/arena/chat-api.mjs` (PI_WEB_ARENA_BRIDGE overrides), timeouts, abort = discard the
    answer but still release the queue, and `busy()`/`listNames()` for status and discovery.
* hub: `getSession({ model, streamFn })` (two additive options), `_runPeer` routes by spec — the SAME
  code creates the child, the role prompt, the journal entry, the caps, the result and the status frames.
  spawnPeer refuses an arena spec up front when no bridge is injected (a useless child is worse than a
  refusal). Steering an arena peer is refused with a reason (one request, not a stream).
* peer-tools: an arena peer's tool list is EMPTY (the bridge is text in/out — stated in the tool's model
  description), and `action:"list"` reports arena availability PLUS real slugs from the live catalog.

ROOT CAUSE FOUND WHILE WIRING IT: the bridge's `chat(message, slug)` matches `x.slug`, a field the live
arena catalog NO LONGER HAS (checked ws/arena/models.json: 1074 entries with publicName/displayName/name
+ id). So its slug lookup can never hit — every arena peer would have failed with "model not found". We
now resolve the slug to the model UUID ourselves (publicName/displayName/name, cached) and hand the bridge
the id it can use; an unknown slug is refused WITH suggestions from the catalog.

tests/arena-peer.test.mjs (33 checks): spec parsing, context flattening, an arena peer through the REAL
spawnPeer path (same session/role/journal/status/result, empty tools, honest zero usage), failures as
results (throwing/empty bridge), the no-bridge refusal, the REAL wrapper driven through a fake bridge
module (serialization, uuid resolution, suggestions, abort, busy), and the missing-bridge file case.

PERFORMANCE (ws-diag/peer-perf.mjs, same role/task/code path): pi backend (deepseek-ai/deepseek-v4.1-flash
on nvidia) 115.0s / 568 tokens and 73.6s / 289 tokens on two runs — the endpoint's queueing, consistent
with the earlier measurements. The arena side needs an arena.ai tab open in the debugged browser (it was
closed at measurement time); run `node ws-diag/peer-perf.mjs --arena` to compare them side by side.
